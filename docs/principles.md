# 原理与架构详解

## 一、为什么在 DNS 层拦截

### 1.1 一次广告加载的完整链路

```
App 启动
  │
  ├─ ① 解析广告服务器域名  ← ★ 我们要在这里下手
  │     ads3-normal-hl.zijieapi.com  →  需要 IP 才能连接
  │
  ├─ ② 建立 HTTPS 连接，请求广告素材
  ├─ ③ 展示广告、上报曝光、计费
  └─ ④ 用户点击 → 跳转
```

**①②③④ 里只有 ① 是"必须成功才能继续"的** —— 解析失败，后面的全部无法进行。

### 1.2 三种拦截手段的对比

| 手段 | 拦在哪 | 优点 | 缺点 |
|------|--------|------|------|
| **改 hosts** | 每台设备 | 简单 | **要逐台改**，iOS 上极麻烦，App 更新/重装可能失效 |
| **拦 IP** | 路由器 / 防火墙 | 覆盖全屋 | **广告服务器 IP 天天变**，维护成本极高 |
| **拦 DNS** ★ | 一台主机 | **域名固定、一处维护、全屋生效、随时可退** | 拦不住已缓存内容；客户端用 DoH 可绕过 |

**本方案选 DNS 的理由**：域名是广告商**最不常变**的东西（换域名要走合规和灰度流程），
而 IP 是**最常变**的（CDN 调度 + 弹性扩容）。拦域名 = 打它的软肋。

### 1.3 dnsmasq 的两种黑洞写法

```conf
# 写法 A：答 0.0.0.0（推荐）
address=/ads3-normal-hl.zijieapi.com/0.0.0.0

# 写法 B：答 NXDOMAIN（更"诚实"，告诉客户端这个域名不存在）
address=/ads3-normal-hl.zijieapi.com/#
```

**本方案用写法 A**，原因：`0.0.0.0` 是"有效但不可路由"的地址，
客户端拿到后会**尝试连接然后立刻失败**（connect refused），整个过程毫秒级；
而 NXDOMAIN 会让某些 App 触发**重试 + 换备用域名**逻辑，反而多打几个请求。

两种写法在日志里的表现：

```
写法 A →  reply ads3-normal-hl.zijieapi.com is 0.0.0.0      ← 被黑洞
写法 B →  config error is REFUSED (NXDOMAIN)                ← 不存在
```

**注意**：`address=/domain/0.0.0.0` **只对该域名本身生效**，不含子域。
若要连子域一起拦，需写成 `address=/example.com/0.0.0.0`（dnsmasq 对 `address=` 的匹配
会同时覆盖该域及其所有子域 —— **这也是本项目坚持写精确完整域名的原因**，
写宽了会连正片一起拦掉）。

## 二、广告域是怎么被发现的

### 2.1 核心洞察：时间戳聚类

DNS 日志长这样（每行一条）：

```
Oct  5 16:54:12 dnsmasq[687996]: query[A] v11-reading-video.qznovelvod.com from 192.168.1.150
Oct  5 16:54:12 dnsmasq[687996]: reply v11-reading-video.qznovelvod.com is 121.40.x.x
Oct  5 16:54:13 dnsmasq[687996]: query[A] ads3-normal-hl.zijieapi.com from 192.168.1.150
Oct  5 16:54:13 dnsmasq[687996]: config ads3-normal-hl.zijieapi.com is 0.0.0.0
```

**关键特征**：广告域**只在广告出现的那一瞬间被查询**，平时完全不出现。

所以工作流是：

1. 用户刷 App 时看到广告 → **记下大概时间**
2. 事后从全量日志里**切出那个时间窗口**
3. 窗口内那些"**只在广告时刻出现、平时不出现**"的域名 = 广告域
4. 补进 `gen_rules.py` → 重新生成 → `pkill -HUP dnsmasq` 生效

工具：

```bash
./scripts/adblock-helper.sh win 3      # 最近 3 分钟的所有查询 ← 主力命令
./scripts/adblock-helper.sh suspect    # 疑似广告域（按关键字特征筛）
./scripts/adblock-helper.sh top        # 查询量 Top30 域名
./scripts/adblock-helper.sh dev        # 各设备查询量（先确认是哪台设备）
```

### 2.2 广告域的名字特征

字节系广告域的命名高度规律，可直接用来筛选：

| 特征 | 例子 | 含义 |
|------|------|------|
| `ads{数字}-normal-hl` | `ads3-normal-hl.zijieapi.com` | **广告接口**（最典型） |
| `-normal-sinf` | `api5-normal-sinfonlinea.fqnovel.com` | 广告计费/曝光上报 |
| `-sign` | `*-sign*.zijieapi.com` | 签名校验（拦了广告请求作废） |
| `is.snssdk.com` | 抖音系上报 | 归因 |
| `praisewindow.*` | `praisewindow.ugsdk.cn` | 激励视频弹窗 |
| `dig.bdurl.net` | 百度统计跳转 | 点击上报 |
| `lf-webcast-*` | `lf-webcast-gr-sourcecdn.bytegecko.com` | 直播/广告素材分发 |

**这套命名规律的价值**：新广告上线时不用抓包，**同命名模式的域名可以直接预判拦截**。

### 2.3 为什么不用关键字规则

很多人喜欢写 `DOMAIN-KEYWORD,ads` 这类规则 —— **在本项目里被明令禁止**。

原因：`ads` 这个关键字会误伤大量正常域名（例如 `ads` 出现在公司名、CDN 名里）。
本项目只接受**精确完整域名**，代价是规则条数少（198 条），收益是**误伤率 0**。

## 三、出门在外为什么也能用

### 3.1 问题：内网 IP 出不去

本机的 DNS 监听地址是内网 IP（如 `192.168.1.2`）。这个地址**只在局域网内有意义** ——
手机在 4G 或别人家 WiFi 下，根本访问不到它。

**为什么不能直接暴露到公网**：

- 家庭宽带的公网 IP 大多是**动态的**（今天这个、明天那个）
- iOS 的「配置 DNS」**只能填 IP，不能填端口** → **必须占标准 53 端口**
- 国内大厂云主机（阿里云/腾讯云）**默认封禁 53 端口**，解封要域名备案 + 工单
- 把 DNS 暴露在公网 = 开放解析器，会被滥用（DNS 放大攻击）

### 3.2 解法：Tailscale 组网

Tailscale 基于 WireGuard，给每台设备分配一个**虚拟内网 IP**（`100.x.y.z`）：

```
本机   →  100.x.y.z     ← dnsmasq 增加监听这个地址
手机   →  100.a.b.c
```

**不管手机接的是哪个网络**，只要 Tailscale 客户端连上，两台设备就在同一个虚拟内网里，
**手机可以像在家里一样直接访问 `100.x.y.z:53`**。

### 3.3 为什么能直接连（P2P）而不是绕服务器

Tailscale 的**控制面**和**数据面**是分开的：

| 平面 | 作用 | 看得到什么 |
|------|------|-----------|
| **控制面**（Tailscale 服务器） | 交换设备公钥、告知彼此的公网地址、协调连接 | 只知道「哪两台设备在通信」，**看不到内容** |
| **数据面**（设备之间） | 实际的 DNS 查询流量 | **端到端加密的 WireGuard 隧道** |

**打洞流程**：

```
① 手机和本机都向控制面报告自己的公网出口地址
② 控制面把双方地址告诉对方
③ 双方同时向对方地址发包 → 各自 NAT 上开一个洞
④ 洞打通 → 建立 P2P 直连 → 之后所有流量走这条直连
⑤ 打洞失败才降级走 DERP 中继（延迟更高，但内容依然加密）
```

**实测结果**：`new contact ... via=direct`、`ping pong in 39 ms` —— **打洞成功，走的是直连**。

### 3.4 为什么 DNS 绕行不影响视频流畅度

这是最常被问的问题：「DNS 跑回你家，视频会不会卡？」

**不会。** 因为两者走的是**完全不同的路径**：

| 环节 | 谁负责 | 频率 |
|------|--------|------|
| **解析域名**（找 CDN 地址） | **家里那台机** | **只在开头查一次**，之后走本地缓存 |
| **传输视频流本身** | **手机直连 CDN** | 每秒数兆，完全不经过家里 |

**所以家里那台机承担的只是"查号台"的角色** —— 实测内存 2.5 MB、CPU 0.0%，
几十台设备一起用都压不垮它。

### 3.5 一个关键配置项：Override local DNS

在 Tailscale 后台（`login.tailscale.com/admin/dns`）添加 nameserver =
本机的 Tailscale IP 后，**必须打开「Override local DNS」**。

**不开的后果**：你的机器只会被当作 `*.ts.net` 域名的解析器 ——
手机查 `ads3-normal-hl.zijieapi.com` 时**根本不会问你的机器**，拦截形同虚设。

**开了的效果**：手机的所有 DNS 查询都转发到你的机器。

## 四、系统为什么是"两层生效"

```
第一层（在家）  dnsmasq 监听 内网IP:53      ← 局域网设备直接访问
第二层（在外）  dnsmasq 监听 TailscaleIP:53 ← 隧道进来的设备访问
                        ↓
                  同一份 adblock-fq.conf
                  同一份 queries.log
```

**两层共用一份规则和一份日志**，所以：

- 新增规则只需要改**一个文件**
- 抓包分析不需要区分"这条是哪台设备、在家还是在外面"—— 日志里有来源 IP，一眼可辨
- 在家的设备走局域网（延迟 < 1ms），在外的走隧道（延迟 ~40ms），各自最优

## 五、日志与运维

### 5.1 日志格式

```
<时间> dnsmasq[PID]: query[类型] <域名> from <来源IP>
<时间> dnsmasq[PID]: reply  <域名> is <结果>            ← 正常解析
<时间> dnsmasq[PID]: config <域名> is 0.0.0.0          ← 被本项目黑洞 ★
```

**过滤技巧**：

```bash
# 只看被拦下的（这就是"拦截统计"）
grep "is 0.0.0.0" queries.log | wc -l

# 按来源设备分组
grep -oE "from [0-9.]+" queries.log | sort | uniq -c | sort -rn

# 某台设备在看什么
grep "from 192.168.1.150" queries.log | tail -50
```

### 5.2 为什么必须做日志轮转

`log-queries` 打开后，**一部手机刷一小时短剧能产生上万行日志**。
不轮转的话，几个月就能写满磁盘（尤其树莓派这类小存储设备）。

`config/dnsmasq-adblock.logrotate` 配置：每天轮转、保留 7 天、压缩归档，
轮转后给 dnsmasq 发 `SIGUSR2` 让它重新打开日志文件句柄。

### 5.3 长期运行的资源占用实测

```
PID      %CPU  %MEM   RSS       ELAPSED
687996   0.0   0.0    2524 KB   34 分钟
```

**结论：这套方案可以跑在任何能装 Linux 的设备上** ——
树莓派、迷你主机、旧笔记本、甚至路由器（OpenWrt 自带 dnsmasq）。
不需要为它单独买大机器。
